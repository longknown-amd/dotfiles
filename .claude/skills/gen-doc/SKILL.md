# Generate Documentation → self-hosted docs site

All GPU engineering docs live in a self-hosted git repo on the docs host.

**Configuration:** the docs host, its OS and shell, the repo paths, the remote URL and the site URL are defined in
`~/.claude/CLAUDE.md` ("Centralized Documentation"). Below, `<docs-host>`, `<remote-url>`, `<docs-root>` and
`<site-url>` stand for those values. Read them from there, and never hard-code them in synced files.

The architecture is:

- **Bare repo (push target):** on `<docs-host>`, reached through `<remote-url>`. Use that URL exactly as written;
  some hosts, such as a Windows host whose SSH shell is `cmd`, need a special transport form.
- **Working tree (built from):** `<docs-root>` on the host, with mkdocs in its own `.venv`
- **Build output:** `<docs-root>/site`, static HTML regenerated by the bare repo's `post-receive` hook
- **Web server:** a static file server for `site/` on port 8000, at **`<site-url>`**

A push to the bare repo triggers the hook: `git pull --ff-only` in `<docs-root>`, then `mkdocs build`. The web
server serves the rebuilt files straight away, so end-to-end propagation takes a few seconds.

The local clone is always `~/docs`. Every step below edits that clone and pushes it.

**Other targets:**
- **Interactive code explainers** (feature walkthroughs, commit reviews): use the `code-walkthrough` skill, which
  builds raw HTML pages and publishes them through this same repo.
- **OneNote:** only when the user explicitly asks for it. The OneNote MCP tools (`mcp__onenote__*`) are still available.

## 0. Check the clone first

- If `~/docs` is missing, clone it with the URL from CLAUDE.md, plus any git config it lists, for example:
  `git clone -c protocol.ext.allow=always "<remote-url>" ~/docs`.
- Check that `git -C ~/docs remote get-url origin` matches `<remote-url>`. If it still points at a host that
  CLAUDE.md calls **legacy**, stop and tell the user rather than pushing there. Repointing the remote is the user's
  call.
- `mkdocs` is usually not installed locally, so verify by fetching the published URL after the push.

The workflow: edit → commit → push to `origin`. The host's hook builds the site whoever pushed.

## 1. Determine the topic and section

Ask the user, or infer from context, what the doc covers. List the existing sections with `ls ~/docs/docs/`
and the nav in `~/docs/mkdocs.yml`. Map the doc to an existing folder, or create a new one if nothing fits.
`index.md` is the landing page that links every section.

Before writing, run `git -C ~/docs pull --ff-only` so you start from the latest revision.

## 2. Write the doc

- Use clear markdown with proper headings, tables and code blocks. Start with a level-1 heading (`# Title`).
- Keep it reference-oriented (facts, architecture, code patterns), not a tutorial.
- Include code snippets where they clarify behaviour. Cite `file:line` and the revision for anything taken from
  a repo, because line numbers drift.
- No emojis unless the user asks for them.
- **Reader-first layout** for reports, evaluations and investigations:
  1. **Summary first:** the question and answer in 2 lines, then 5-10 highlight bullets, then one key-figures
     table with the numbers a decision rests on.
  2. **Main body next:** scoreboard and charts, recommendations, setup, then the per-item details.
  3. **Appendices last:** detailed findings, harness or tooling issues and fixes, caveats, and step-by-step traces
     or raw logs. Collapse long traces (`<details>` in HTML).
- Keep every number identical between the summary, the body and any HTML version generated from the same source.
  Renumber cross-references ("see section N", "Appendix X") after reordering sections.

## 3. Save to the central docs path

Write the file to `~/docs/docs/<section>/<filename>.md` (lowercase, hyphenated filename).

**Raw HTML pages** (self-contained or interactive) also go under `~/docs/docs/<section>/`. MkDocs copies them
unchanged. Their nav entries must use an **absolute path** (see step 4).

## 4. Update mkdocs.yml nav

Read `~/docs/mkdocs.yml`, then add the new page under the matching nav section. Create a new top-level nav entry if
the section doesn't exist.

```yaml
  - Some Section:
    - "Some Page": some-section/some-page.md                    # markdown: relative path
    - "Some Explainer (interactive)": /some-section/explainer.html   # raw HTML: absolute path
```

## 5. Update the landing page

Read `~/docs/docs/index.md` and add a link to the new doc under the matching section. For a new section, add a
heading and a one-line description.

If `index.md` is missing sections that exist in the nav, mention that to the user and offer to fill the gap;
don't do it silently.

## 6. Local build check (optional)

Only when `mkdocs` is available locally:

```sh
cd ~/docs && mkdocs build --strict --site-dir /tmp/docs-site-check
```

If `mkdocs` isn't installed, skip this step. A build error then shows up as the push output from the hook, or as a
stale page (see Troubleshooting).

## 7. Stage, then ask before pushing

Stage the new or changed files but **don't commit or push automatically**:

```sh
git -C ~/docs add docs/<section>/<filename>.md docs/index.md mkdocs.yml
git -C ~/docs status --short
```

Show the user the staged diff summary and a proposed commit message (`docs(<section>): <what>`), then ask whether
to commit and push.

**Exception:** if the user's request already said to publish or push (e.g. "publish it to the docs server"), that
is the approval. Commit and push without asking again.

Pushing:

```sh
git -C ~/docs commit -m "<message>"
git -C ~/docs push origin main
git -C ~/docs status -sb | head -1     # must NOT say "ahead"
```

The hook's `git pull` and `mkdocs build` output comes back as `remote:` lines in the push output; read them for
build errors. Some hosts print an authentication banner on SSH; that's noise. If `status -sb` still says `ahead`,
retry the push (up to 3 times, a few seconds apart) before reporting a failure.

## 8. Verify propagation

Wait about 3 seconds, then confirm the new content is live, using a cache-buster:

```sh
curl -sS -o /dev/null -w "%{http_code}\n" "<site-url><path>"            # expect 200
curl -sS "<site-url><path>?cb=$(date +%s)" | grep -c "<unique string from new doc>"
curl -sS "<site-url>?cb=$(date +%s)" | grep -o "Build Date UTC : [^<]*"
```

The markdown page URL is `/<section>/<filename>/` (directory style); a raw HTML page stays at
`/<section>/<filename>.html`. A recent `Build Date UTC` confirms the rebuild ran. If the page returns 404, the
string is missing, or the timestamp didn't advance, go to Troubleshooting.

## 9. Report

Tell the user:
- the local file path
- that the changes are pushed and live at the full URL under **`<site-url>`** (or that they're staged and
  awaiting approval)
- the diagnostic from Troubleshooting, if verification failed

## Troubleshooting

If the published page doesn't reflect a push:

| Symptom | First check |
|---|---|
| `git push` rejected, or `status -sb` still says `ahead` | Retry. Then check `ssh <docs-host>` works, and that `origin` is exactly `<remote-url>` (with any git config CLAUDE.md lists) |
| `does not appear to be a git repository` | The remote URL form is wrong for the host's shell; use the URL from CLAUDE.md verbatim |
| Push succeeds but the build timestamp didn't move | Read the `remote:` lines of the push output. Then check the host's working tree is at your commit (`git -C <docs-root> log -1` over SSH) |
| `mkdocs build` errored | Fix the markdown or nav and push again; CLAUDE.md names a manual build script if one exists |
| Page completely unreachable | Check the web server on the host: is port 8000 listening, and is the process from CLAUDE.md running? The host may also be asleep or signed out; tell the user rather than restarting things yourself |
| A raw HTML page 404s but its markdown siblings work | Check the nav entry uses an absolute path (`/section/page.html`) and the file is under `docs/` |

Host-specific commands (shell, paths, how the server starts) are in CLAUDE.md, not here.
